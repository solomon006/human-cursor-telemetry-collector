# Схема данных MotorCursor

Данный документ описывает структуру данных, собираемых приложением MotorCursor.

> **Главный принцип**: Raw log (сырой лог от Godot) является единственным источником истины. Normalized (нормализованные) и Derived (вычисляемые) таблицы — это воспроизводимые представления, которые строятся на основе сырых логов.

Архитектура пайплайна данных состоит из 3 слоев:
1. **Layer 1: Raw Collection Schema** (Сбор сырых данных в Godot)
2. **Layer 2: Normalized Dataset Schema** (Табличное представление базовых фактов)
3. **Layer 3: Derived Analytics Schema** (Аналитические метрики и кинематика)

---

## Формат идентификаторов (ID Format)

В примерах ниже используются упрощенные ID (например, `p_0001`, `s_0001`). В реальном приложении для уникальности `participant_id` и `session_id` генерируются как строка с префиксом, UTC timestamp и случайным hex-суффиксом:

```text
p_YYYYMMDDTHHMMSSZ_<random_hex>
s_YYYYMMDDTHHMMSSZ_<random_hex>
```

`trial_id` формируется как `t_[session_id]_[trial_index]`, где `trial_index` форматируется четырьмя цифрами.

---

## Структура хранения (Dataset Directory)

В конечном виде датасет организуется в следующую структуру файлов:

```text
dataset/
├── README.md                   <-- (Planned / Not generated by normalizer yet)
├── trial_plan.json             <-- (Planned / Not generated by normalizer yet)
├── raw_sessions/               <-- Layer 1 (Source of truth)
│   ├── s_0001_raw.jsonl
│   └── s_0002_raw.jsonl
├── participants.jsonl          <-- Layer 2 (Normalized views)
├── sessions.jsonl
├── trials.jsonl
├── input_events.jsonl
├── block_events.jsonl
├── practice_events.jsonl
├── quality_events.jsonl
├── form_events.jsonl
└── derived_features.parquet    <-- Layer 3 (Planned / Future)
```

## Layer 1: Raw Collection Schema

**Исходный лог**, который Godot-приложение пишет "на лету" во время сессии. Каждая строка — это событие, маркированное полем `kind`. Файл пишется последовательно, как append-only журнал в рамках активной сессии. Движок не выполняет тяжелую математику, его задача — зафиксировать факты ввода с максимальной точностью по времени. Данные регулярно сбрасываются на диск; при аварийном завершении возможна потеря последних строк, которые еще не были flush-нуты.

### Структура `raw_sessions/s_XXXX_raw.jsonl`

Файл содержит следующие типы событий (`kind`):
- `session_start` / `session_end`
- `practice_start` / `practice_end`
- `block_start` / `block_end`
- `trial_start` / `trial_end`
- `event` (события мыши: motion, button_down, button_up — как в trial-контексте, так и в form-контексте)
- `quality_event` (lost_focus, window_resized, missed_click)
- `form_start` / `form_completed`
- `form_click`

Пример:
```json
{"kind":"session_start","data":{"session_id":"s_0001","participant_info":{"participant_id":"p_0001"}}}
{"kind":"practice_start","data":{"session_id":"s_0001","planned_practice_trials":10}}
{"kind":"trial_start","data":{"trial_id":"t_s_0001_0001","t_us":184002311,"condition":{"distance_level_px":600,"target_size_level_px":32},"placement":{"clamped_to_viewport":false}}}
{"kind":"event","data":{"event_type":"mouse_motion","trial_id":"t_s_0001_0001","t_us_abs":184010020,"position":{"x":320.0,"y":540.0},"relative":{"dx":2.1,"dy":-1.0}}}
{"kind":"quality_event","data":{"event_type":"lost_focus","trial_id":"t_s_0001_0001","t_us":184050000}}
{"kind":"trial_end","data":{"trial_id":"t_s_0001_0001","success":false,"quality":{"valid_trial":false,"invalid_reasons":["lost_focus"]}}}
{"kind":"session_end","data":{"session_id":"s_0001"}}
```

### Фактические payload-блоки

Пример выше сокращен. Реальные payload-объекты содержат больше полей:

- `session_start.data`: `session_id`, `participant_id`, `t_us`, `started_at_utc`, `participant_info`, `app`, `system`, `display`, `input`, `experiment`, `quality` (начальное состояние — все счётчики равны нулю).
- `session_end.data`: `session_id`, `participant_id`, `t_us`, `ended_at_utc`, `duration_us`, `session_completed`, `quality` (финальные счётчики: `lost_focus_count`, `window_resize_count`, `total_trials`, `valid_trials`, `valid_session`).
- `trial_start.data`: `trial_id`, индексы trial, `block_index`, `is_practice`, `trial_type`, `t_us`, `start_cursor`, `condition`, `target_acquisition_rule`, `target`, `placement`, `task_geometry`, `timing.target_shown_t_us`, опционально `previous_target_click`.
- `trial_end.data`: итоговый `success`, финальные `timing`, `result`, `quality`, а также повтор ключевых полей trial (`condition`, `start_cursor`, `target`, `task_geometry`) для удобства нормализации.
- `event.data`: общие поля события ввода (`event_id`, `participant_id`, `session_id`, индексы события, timestamps, `position`, `buttons`, `raw`). В trial-контексте содержит `trial_id`, `event_index_trial`, `t_us_trial`, `phase` и `state`. В form-контексте вместо этого содержит `context: "form"`, `event_index_form`, `t_us_form` / `t_ms_form` (поля `trial_id`, `phase`, `state` отсутствуют). В текущей v1-схеме `position` берется из `InputEventMouseMotion.position` / `InputEventMouseButton.position` в viewport pixels. Для `mouse_motion` дополнительно пишется `relative` из `InputEventMouseMotion.relative`; для событий кнопки дополнительно пишется `button`.

## Layer 2: Normalized Dataset Schema

Это табличная раскладка фактов, генерируемая Python-скриптом `normalize_raw_sessions.py`. Она не содержит сложной ML-аналитики, но связывает события в удобные реляционные таблицы `.jsonl`. 

*(Внимание: некоторые примеры JSON ниже приведены в сокращенном виде для удобства чтения).*

### Правила нормализации и merge

- `session_start` создает строку в `sessions.jsonl`; `session_end` обновляет ту же строку по `session_id`.
- `trial_start` создает строку в `trials.jsonl`; `trial_end` обновляет ту же строку по `trial_id`.
- При совпадении ключей используется обычное обновление словаря: значения из `session_end` / `trial_end` перезаписывают значения из start-событий.
- Для `trials.jsonl` это означает, что верхнеуровневый `t_us` после нормализации содержит время конца trial, а не время появления цели. Для анализа времени используйте `timing.*`.
- Если для `trial_start` нет соответствующего `trial_end` (например, приложение закрыто в середине задания), нормализатор оставит неполную строку trial. Такие строки нужно отфильтровывать или обрабатывать отдельно в аналитическом слое.

### `block_events.jsonl`
События начала (`block_start`) и конца (`block_end`) блоков эксперимента (групп из N заданий, между которыми участник делает перерыв).

Пример:
```json
{
  "kind": "block_start",
  "session_id": "s_0001",
  "participant_id": "p_0001",
  "block_index": 1,
  "t_us": 184000000,
  "completed_trials_before_block": 0,
  "trials_per_block": 100
}
```

Пример `block_end`:
```json
{
  "kind": "block_end",
  "session_id": "s_0001",
  "participant_id": "p_0001",
  "block_index": 1,
  "t_us": 185500000,
  "duration_us": 1500000,
  "completed_trials_total": 100,
  "reason": "scheduled_break"
}
```

`reason` может принимать значения `"scheduled_break"` (перерыв между блоками), `"experiment_completed"` (завершение всего эксперимента) или `"user_paused"` (участник нажал Escape для паузы).

### `practice_events.jsonl`
События `practice_start` и `practice_end`, фиксирующие прохождение разминочных заданий.

Пример:
```json
{
  "kind": "practice_end",
  "session_id": "s_0001",
  "participant_id": "p_0001",
  "t_us": 184500000,
  "completed_practice_trials": 10
}
```

### `quality_events.jsonl`
Аномальные события среды или ошибки пользователя во время trial, которые могут повлиять на качество данных и учитываются при валидации попытки.

Возможные значения `event_type`:
- `lost_focus` — окно приложения потеряло фокус.
- `window_resized` — размер окна изменился. Дополнительные поля: `viewport_width_px`, `viewport_height_px`.
- `missed_click` — пользователь кликнул мимо цели (pointer_down или pointer_up вне target bbox). Дополнительное поле: `position`.

Пример `lost_focus`:
```json
{
  "session_id": "s_0001",
  "participant_id": "p_0001",
  "trial_id": "t_s_0001_0042",
  "event_type": "lost_focus",
  "t_us": 184050000
}
```

Пример `missed_click`:
```json
{
  "session_id": "s_0001",
  "participant_id": "p_0001",
  "trial_id": "t_s_0001_0042",
  "event_type": "missed_click",
  "t_us": 184055000,
  "position": { "x": 800.0, "y": 450.0 }
}
```

### `form_events.jsonl`
События натуралистической фазы сбора данных. После завершения point-and-click заданий участнику предлагается заполнить стилизованную веб-форму (имитация реальной формы регистрации). Это позволяет собирать паттерны движения курсора в контексте, приближенном к реальному использованию интерфейсов.

Форма содержит следующие интерактивные элементы: `email1_btn`, `email2_btn`, `country_option`, `agree_check`, `captcha_btn`, `captcha_box`, `submit_btn`.

#### События мыши на форме

Во время взаимодействия с формой непрерывно логируются все события мыши (motion, button_down, button_up) в том же формате `event`, что и в trial-контексте, но с дополнительными полями:
- `context: "form"` — отличает от trial-событий.
- `event_index_form` — порядковый номер события внутри формы (вместо `event_index_trial`).
- `t_us_form` / `t_ms_form` — время относительно показа формы (вместо `t_us_trial` / `t_ms_trial`).
- Поля `trial_id`, `phase`, `state` отсутствуют.

#### `form_start`
Записывается при загрузке экрана формы. Содержит начальную позицию курсора, размеры viewport и снимок bounding box всех интерактивных элементов.

```json
{
  "kind": "form_start",
  "session_id": "s_0001",
  "participant_id": "p_0001",
  "t_us": 186000000,
  "cursor_pos": { "x": 960.0, "y": 540.0 },
  "viewport": { "width": 1920, "height": 1080 },
  "elements": {
    "email1_btn": { "bbox": { "x": 735, "y": 280, "width": 450, "height": 38 }, "visible": true, "disabled": false },
    "submit_btn": { "bbox": { "x": 735, "y": 620, "width": 180, "height": 45 }, "visible": true, "disabled": true }
  }
}
```

#### `form_click`
Записывается при каждом отпускании левой кнопки мыши на экране формы. Содержит полную информацию для анализа по Fitts' law.

```json
{
  "kind": "form_click",
  "session_id": "s_0001",
  "participant_id": "p_0001",
  "form_click_index": 1,
  "context": "form",
  "t_us": 186050000,
  "t_us_form": 50000,
  "click_position": { "x": 850.0, "y": 295.0 },
  "pointer_down_position": { "x": 849.5, "y": 294.8 },
  "start_cursor": { "x": 960.0, "y": 540.0 },
  "distance_from_last_click_px": 271.3,
  "time_since_last_click_ms": null,
  "click_hold_time_ms": 58.4,
  "element": {
    "element_id": "email1_btn",
    "bbox": { "x": 735, "y": 280, "width": 450, "height": 38 },
    "center": { "x": 960.0, "y": 299.0 },
    "effective_width_px": 412.5,
    "id_shannon": 0.89
  },
  "all_elements": {
    "email1_btn": { "bbox": { "x": 735, "y": 280, "width": 450, "height": 38 }, "visible": true, "disabled": false },
    "submit_btn": { "bbox": { "x": 735, "y": 620, "width": 180, "height": 45 }, "visible": true, "disabled": true }
  }
}
```

Поле `element` равно `null`, если клик произошёл вне всех интерактивных элементов. `all_elements` содержит актуальный снимок bbox и состояния всех элементов на момент клика (некоторые элементы, например `captcha_box`, могут менять `visible` в процессе).

#### `form_completed`
Записывается при нажатии кнопки «Продолжить».

```json
{
  "kind": "form_completed",
  "session_id": "s_0001",
  "participant_id": "p_0001",
  "t_us": 186200000,
```

## Layer 3: Derived Analytics Schema (Planned / Future)

Здесь живут вычисляемые метрики: пересчитанные скорости (velocity), ускорения, выявление перехлестов (overshoots) и анализ плавности (jerk, straightness). **Эти данные не пишутся в Godot.** Они рассчитываются постфактум Python-скриптами, поскольку алгоритмы (например, фильтры сглаживания или детекция старта движения) могут обновляться со временем.

Некоторые базовые времена (`reaction_time_ms`, `movement_time_ms`, `click_hold_time_ms`) уже есть в `trials.timing`. В `derived_features` они могут быть продублированы как удобные признаки для ML, но источником правды остается raw log и нормализованный `trials.jsonl`.

## Consent Flow

Перед сбором данных участник должен отметить consent checkbox на приветственном экране. Если согласие не дано, кнопка старта остается недоступной и сессия сбора не начинается. В датасете сохраняется только факт согласия (`participants.consent_given`); текст согласия и версия формы должны храниться отдельно в документации исследования или в будущем поле вроде `consent_form_version`.

## Edge Cases

- **Аварийное завершение приложения**: raw log уже записан построчно, но последние строки после предыдущего flush могут отсутствовать.
- **Закрытие окна во время trial**: сессия завершится через `session_end`, но активный trial может остаться без `trial_end`.
- **Неполный trial в нормализованных данных**: если есть `trial_start`, но нет `trial_end`, строка попадет в `trials.jsonl` без финальных `timing`, `result` и `quality`.
- **Возврат участника после перерыва**: приложение может продолжить эксперимент с тем же `participant_id`, но с новым `session_id`.

## Важные архитектурные замечания (Сбор в Godot)

1. **Godot Events**: Координаты считываются через `_input(event)`, а не `_process(delta)`. Это позволяет сохранять события ввода без привязки к FPS.
2. **Отключение накопления ввода**: При старте Godot задается `Input.use_accumulated_input = false` для фиксации атомарных движений.
3. **Хранение плохих попыток**: Ни один `trial` не удаляется во время сессии. Ошибки (вывод курсора за окно, клик другой кнопкой) отмечаются флагом `"valid_trial": false` и попадают в `"invalid_reasons"`.
4. **Режим курсора**: В v1 используется `Input.MOUSE_MODE_VISIBLE`. Основная позиция курсора берется из `event.position`, а `event.relative` сохраняется рядом как смещение текущего motion event. Оба значения уже прошли через input stack ОС/Godot и не считаются сырыми hardware counts мыши.
